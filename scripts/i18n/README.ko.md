# 업스트림 업데이트 후 한국어·영어 패치 유지하기

영문 상세: [README.md](README.md). 이 포크의 원격 저장소는
`https://github.com/sehoon123/ARTEX.git`입니다.

**원칙: 화면만 번역하고 모델 입력은 번역하지 않습니다.** 업스트림이 프롬프트나
도구 지시문을 개선하면 **새 원문을 그대로 받아들입니다**. 옛 중국어 버전으로
고정하는 것도, 한국어/영어로 치환하는 것도 아닙니다. 프롬프트 언어 변경은
모델 동작에 영향을 줄 수 있으므로 별도 비교 검증 대상으로 분리합니다.

순서: 별도 브랜치 병합 → 누락/충돌 해결 → 검증 → EN/KO 화면 확인 → 승인 후 반영.
AI에게 맡길 때는 마지막 [복사용 요청문](#5-다음번-ai에게-맡기는-복사용-요청문)을 사용하세요.

## 1. 업데이트를 별도 브랜치에서 병합

아래 병합은 **업데이트를 승인한 경우** 저장소 루트에서 실행합니다. 작업 폴더가
더럽다면 먼저 작업을 보존하고 중단하세요. 로컬 `main`이 사용하려는 포크 기준인지도 확인합니다.

```bash
git status --short
git remote -v                        # origin=sehoon123/ARTEX, upstream=Autumn-27/ARTEX
git switch main
# 처음 복제했다면 한 번만 등록:
# git remote add upstream https://github.com/Autumn-27/ARTEX.git
git fetch upstream
git rev-parse HEAD upstream/main      # 검증 기록에 두 SHA 저장
git diff --stat HEAD...upstream/main  # 새 기능/변경 파일 확인
git switch -c upstream-update-$(date +%Y%m%d-%H%M)
git merge upstream/main
```

### 충돌이 나면

`git diff --name-only --diff-filter=U`로 파일을 확인하고, **전체 파일에 무조건
ours/theirs를 적용하지 마세요**. 해결한 파일만 `git add <파일>` 후
`git merge --continue`로 병합을 마칩니다. 아직 병합 중이고 취소하려면 변경 작업을
별도로 보존한 뒤 `git merge --abort`를 사용하세요. 이미 끝난 병합에는 적용되지 않습니다.

| 충돌 위치 | 보존·복원할 것 |
| --- | --- |
| UI `.tsx` | 업스트림의 새 로직 + 표시 위치의 `tr()`. 중국어 원문이 사전 키이므로, 같은 문구의 일반 JSX/표시 속성은 사전 보충 후 `i18n:wrap`으로 재적용 가능. 파일 전체 복원 수단은 아님. |
| 동적 API 라벨·날짜·상태 | `builtin-labels.ts`의 `display…()` 호출/가져오기, `getLocale()`, `statusMeta()`의 표시 번역은 wrap이 재생성하지 않음. 도구/Agent/채팅/MCP/Skill/툴팁 호출부를 직접 비교. |
| `en.json` / `ko.json` | 양쪽의 필요한 키와 수동 번역 보존. 중국어 **키는 유지하고 값만 번역**. `{n0}` 등 자리표시자는 개수까지 일치. 중복 키나 문법 오류는 검사로 확인. |
| 메타데이터 JSON | 한쪽 스냅샷을 임의 채택하지 말고, 병합된 Go 소스를 검토한 뒤 아래 `i18n:catalog` 절차 적용. |
| `package.json` / 워크플로 / README | 업스트림 의존성·새 기능 설명과 포크의 `i18n:*` 스크립트, CI, EN/KO 안내를 함께 보존. lockfile 불일치는 숨기지 말고 해결. |

특히 다음 diff를 검토하세요(루트, 아직 `main`에 반영하기 전).

```bash
git diff main -- web/src scripts/i18n web/package.json .github/workflows README.md README.ko.md
```

검사 통과만으로 동적 라벨 호출부가 모두 보존됐다고 볼 수 없습니다. 저장값·ID·상태값·
정규식·스키마·모델 프롬프트를 번역하거나, 알려지지 않은 API 내용을 무조건 `tr()`로 감싸지 마세요.

## 2. 누락 확인 → 번역 → 한 번에 검증

필요 도구: **Node 22 이상**, `go.mod`에 지정된 **Go**, 기존 프론트엔드 의존성.

```bash
cd web
npm ci
npm run i18n:check
# 검사 실패는 새로운 UI 문구 또는 내장 메타데이터 변경을 뜻할 수 있습니다.
```

### 내장 이름·설명 변경이 보고된 경우

먼저 Go 소스의 변경을 읽으세요. 실제 실행 도구나 서버는 실행하지 않습니다.

```bash
npm run i18n:catalog
```

이 명령은 **검토한 소스 기본값의 표시용 스냅샷만 갱신**합니다. DB나 백엔드,
기존 번역은 수정하지 않습니다. 새 도구의 `builtin.tool.<key>.summary`가 없으면
스냅샷을 갱신한 뒤에도 실패하며 누락된 키를 표시합니다. 두 사전에 짧은 UI 요약을
작성하세요. 모델이 사용하는 긴 설명/지시문을 바꾸는 작업이 아닙니다.
기존 요약도 소스의 의미 변화에 맞는지 검토해야 합니다.

### UI 번역 추가

```bash
npm run i18n:extract
# API를 사용하려면 직접 설정한 자격 증명 필요:
# export OPENAI_API_KEY=...
# 또는 export ANTHROPIC_API_KEY=...
npm run i18n:sync
npm run i18n:verify
```

`i18n:sync`는 누락된 항목만 번역하고 표시 위치를 감쌉니다. 기존 수동 번역은
덮어쓰지 않습니다. 연결/응답/플레이스홀더 검증 실패는 성공으로 처리하지 않습니다.
유효한 번역 API가 없다면 `web/src/lib/i18n/en.json`과 `ko.json`에 누락 항목을 직접
추가한 뒤 `npm run i18n:wrap` → `npm run i18n:verify`를 실행하세요.
`{n0}` 같은 자리표시자는 개수까지 유지해야 합니다. 중국어 문구가 조금 바뀌어 새 키로
나오면 비슷한 기존 번역을 찾아 재사용하되 의미 변화도 검토하세요. 동적 사용이 있을 수
있으므로 추출에 안 나온 옛 키를 일괄 삭제하지 마세요.

### 검사 메시지별 다음 행동

아래 npm 명령은 `web/`에서 실행합니다. `i18n:check`는 첫 단계 실패 시 멈추므로
해결한 뒤 다시 실행해야 다음 문제(예: 카탈로그 변경)가 보일 수 있습니다.

| 메시지/상황 | 다음 행동 |
| --- | --- |
| `missing en/ko` | `i18n:extract`로 목록 확인 → 두 사전에 추가 → `i18n:wrap`. extract는 누락이 있어도 종료 코드 0이므로 통과 판정은 check/verify로 함. |
| `file(s) need wrapping` | 키는 있지만 표시 호출이 빠짐. `i18n:wrap` 후 diff 검토. |
| `review these display/key or nested-expression semantics manually` | 지적된 위치의 데이터 흐름 검토. 표시 전용이면 수동 `tr()` 또는 내부 표현식부터 처리. 저장/전송 값이면 원문 유지하고 표시 경계와 검사 방식을 조정. 무조건 예외 처리하지 않음. |
| `needs a reviewed client boundary` | 클라이언트 컴포넌트인지 확인. 서버 설정/metadata에 검사 통과용 `"use client"`나 번역 import를 추가하지 말고 클라이언트 표시 위치로 분리. |
| `Built-in metadata changed` | 소스 의미 검토 → `i18n:catalog` → 바뀐 요약/라벨 검토. 스냅샷 갱신만으로 번역 내용이 최신이 되지는 않음. |
| `missing builtin display translations` | 보고된 키를 두 사전에 직접 작성. **새 `builtin.tool.<key>.summary`는 extract/sync만으로 생성되지 않음**. |
| `Unsupported…` / 카탈로그 중복 | 업스트림 선언 구조가 달라졌는지 정적 파서와 테스트를 검토. 검사를 지우거나 ARTEX 도구를 실행해 목록을 얻지 않음. |
| JSON/placeholder/API 오류 | 사전 중복·빈 값·자리표시자를 고침. API가 없거나 실패하면 위 수동 경로 사용. 소스부터 강제로 감싸지 않음. |

`i18n:verify` = 회귀 테스트 + 번역/내장 메타데이터 검사 + 실제 정적 프론트엔드 빌드.
포크의 `localization-check` GitHub Actions도 같은 명령을 실행합니다.
단, 검사 통과가 모든 동적 화면의 번역이나 번역 품질까지 보장하지는 않습니다.

## 3. 웹에서 확인할 것

### 백엔드 없이 빠르게 확인

별도 브라우저 프로필(실제 토큰 없음), 백엔드·실제 자격 증명 없이 실행하세요.
저장소 루트에서:

```bash
cd web
NEXT_PUBLIC_MOCK=1 npm run dev -- -p 3917 -H 127.0.0.1
```

`http://127.0.0.1:3917`에서 왼쪽 아래 사용자 메뉴의 English/한국어로 전환합니다.
이 플래그는 **해당 dev 명령에만** 지정하세요. 확인 후 Ctrl+C로 종료하며,
배포 빌드의 환경/`.env*`에 `NEXT_PUBLIC_MOCK=1`이 남아 있으면 안 됩니다.

- mock은 빠른 표시 점검 수단이지 **네트워크 격리 장치가 아닙니다**. 직접 fetch/SSE,
  다운로드·외부 링크는 중앙 mock 경로를 우회할 수 있습니다. 개발자 도구에서 요청을
  확인하고 실행/삭제/업데이트/외부 연결은 누르지 마세요. 그런 제어 검사는 localhost
  밖 요청을 차단하는 별도 inert fixture 환경이 필요합니다.
- 샘플 작업명·로그·보고서·모델/사용자 콘텐츠는 중국어가 남는 것이 정상입니다.
  mock 도구/Agent 기본값도 현재 소스 스냅샷과 달라 표시 helper가 원문을 보존할 수
  있습니다. 이를 없애려고 출처/일치 조건을 느슨하게 바꾸지 마세요.
- 데이터가 비어 있거나 기능이 꺼져 숨겨진 분기는 별도 샘플이 필요합니다. 예를 들어
  모델 설정의 토큰 통계는 mock 스위치를 켜야 보이고, `daily=[]`이면 차트·툴팁은
  보이지 않습니다. mock 성공은 전체 화면이나 실제 DB 검증을 뜻하지 않습니다.

EN과 KO 각각에서 데이터가 있는 목록, 검색, 상세 화면, 버튼, 선택 메뉴, 툴팁,
팝업, 폼 검증과 알림을 확인하세요. 특히 새 기능과 API로 내려오는 표시 항목은
소스 문구 검사만으로 빠질 수 있습니다. 자동 추출은 한자/중문 구두점 및 기존 `tr()`
키 중심이므로, 신규 **영어 UI의 한국어 번역**도 수동 확인해야 합니다.

- 도구/Agent/규칙의 저장 요청에서 원래 ID·설명·스키마·기본값·규칙이 유지되는지 확인.
- 실행/삭제/외부 연결 버튼 검사는 실제 대상이 아닌 격리된 로컬 모의 API로 수행.
- 사용자/외부 MCP/Skill 콘텐츠, 보고서·로그·모델 출력, 편집 가능한 원문은 자동 번역하지 않음.
- 오래된 DB 설명이나 사용자가 편집한 기본값은 현재 스냅샷과 일치하지 않으면 원문으로 표시.
- 명령 차단 규칙 이름은 원문 유지(중국어 예약 이름 포함). API에 내장 출처 필드가 없고 사용자도 같은 이름을 쓸 수 있어 이름만으로 번역하지 않음.
- 내장 자산 규칙 설명은 내장 여부와 종류·패턴·설명이 모두 소스 기본값과 일치할 때만 번역.

## 4. 포크 버전을 빌드·설치

**업스트림 Docker 이미지나 업스트림 릴리스에는 이 포크의 패치가 없습니다.**
설정 → **버전 및 업데이트 → 지금 업데이트 / …(으)로 업데이트**는
`selfupdate/github.go`에 고정된 `Autumn-27/artex` 릴리스를 설치합니다.
**업데이트 확인과 실제 설치는 다릅니다.** 번역을 유지하려면 여기서 설치하지 말고
병합·검증된 포크를 다시 빌드하세요. 실수로 설치했다면 DB 변경 가능성이 있으므로
오래된 바이너리로 무작정 되돌리지 말고, 해당 업스트림 버전 이상을 반영한 포크로 복구하세요.

반영 전 완료 기준:

- [ ] 기준 포크/업스트림 SHA와 변경 파일 기록; 충돌과 수동 표시 helper 검토 완료.
- [ ] `npm run i18n:verify` 성공; 새 문구 두 언어와 표시/원문 경계 확인.
- [ ] 새 화면·변경 컴포넌트 EN/KO 확인; 못 본 분기와 의도한 원문을 별도 기록.
- [ ] 번역을 위한 프롬프트/백엔드/저장 payload 변경 없음(업스트림 자체 변경과 구분).
- [ ] 승인 후 업데이트 브랜치에서 검토한 파일만 커밋하고 `main`에 fast-forward 반영.
  불가능하면 중단해 재검토. `origin`이 포크인지 확인 후에만 `main` 푸시.
- [ ] 해당 커밋 SHA의 포크 `localization-check` CI 성공 확인. 바이너리 빌드/릴리스는 별도 승인.

빌드·설치를 승인했다면:

1. 포크의 GitHub → **Actions → build-binary → Run workflow**에서 검증한 브랜치 선택.
2. WSL용 Linux x86-64 파일이 필요하면 targets를 `linux/amd64`로 지정.
3. 릴리스를 만들지 않으려면 tag를 비워 둠.
4. 실행의 소스 SHA가 검증한 커밋인지 확인하고 `artex-binaries`의 ZIP과 `SHA256SUMS` 다운로드.
5. ZIP 체크섬 확인 후 서비스를 중지하고 바이너리·설정·DB·데이터를 백업한 뒤 바이너리 교체.
   설정·DB·데이터 디렉터리는 덮어쓰지 않음. DB 마이그레이션이 있으면 바이너리만 되돌리는 것은 안전한 롤백이 아님.
6. 실제 설치본에서 버전/SHA·EN/KO 전환·내장 UI·PostgreSQL 연결을 확인.
   개발 서버의 번역 화면을 설치 검증으로 대신하지 않음.

이 워크플로는 EN/KO 정적 UI를 Go 바이너리에 포함하도록 구성되었습니다.
로컬 `web/out`만 빌드해도 기존 바이너리의 내장 UI가 바뀌는 것은 아닙니다.
Docker는 필요 없지만 PostgreSQL은 필요합니다. **WSL1의 실제 실행/PTY/DB 연결은
별도로 검증해야 하며, 프론트엔드 검사 통과로 호환성을 보장하지 않습니다.**

## 5. 다음번 AI에게 맡기는 복사용 요청문
