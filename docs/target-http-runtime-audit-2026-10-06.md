# Target HTTP runtime audit — 2026-10-06

## Scope and safety

This audit exercised the deployed ARTEX binary at commit/version `39e054d` and
its embedded proxy on `127.0.0.1:8788`. The backend remained healthy on
`127.0.0.1:8787` before and after the probes.

All origins were temporary listeners bound to loopback. The HTTPS origin used a
one-day throwaway certificate, and clients verified the certificate generated by
the embedded MITM against ARTEX's local CA; no client-side `-k`/insecure bypass
was used. Chromium was placed behind a temporary allowlist proxy which forwarded
only `localhost`/loopback URLs to ARTEX and rejected its background requests
before they could reach ARTEX. Temporary certificates, bodies, profiles, and
receiver logs were deleted after each run.

No real target, target log, credential, authenticated API, or persistent setting
was used. ARTEX was not restarted. The persistence check queried only aggregate
SQLite values; it did not read the pre-existing exchange's host, URL, headers, or
body.

## Method (conceptual commands)

1. Confirm the running executable, listener addresses, Git revision, health, and
   locally installed client versions.
2. Start loopback-only HTTP and HTTPS receivers on ephemeral ports. Record the
   request line, sanitized headers, body length/hash, and negotiated TLS summary.
3. Route requests explicitly through `http://127.0.0.1:8788`, clearing
   `NO_PROXY` where necessary. For HTTPS, use ARTEX's
   `data/traffic/_ca/mitmproxy-ca-cert.pem` as the trust anchor.
4. Exercise absent/default/explicit UAs, redirects, a chunked request, a 1 MiB
   request, a chunked response, and available curl/Python/Go/Node/Git/Chromium
   clients. A marked curl request emulated the native HTTP tool's documented
   local-proxy hop marker.
5. Compare direct and proxied requests, then query the traffic index read-only
   before and after:

   ```text
   curl --noproxy '' --proxy http://127.0.0.1:8788 http://127.0.0.1:<port>/...
   curl --noproxy '' --proxy http://127.0.0.1:8788 \
        --cacert data/traffic/_ca/mitmproxy-ca-cert.pem https://localhost:<port>/...
   HTTP_PROXY=http://127.0.0.1:8788 HTTPS_PROXY=... NO_PROXY= \
        NODE_USE_ENV_PROXY=1 node <local-fetch>
   sqlite3 -readonly data/traffic/_index/index.sqlite \
        'select count(*), coalesce(max(ts),0) from exchanges;'
   ```

The host clients were curl 8.22.0, Python 3.14.8 with requests 2.34.2,
Go 1.27.1, Node 26.10.0, Git 2.55.0, and Chromium 152.0.7977.82 on Linux.
The recognizable scanner CLIs checked by the audit were not installed.

## Results

### User-Agent policy at the deployed proxy

`<browser>` below is ARTEX's configured desktop profile (`Chrome/141` on
`Windows NT 10.0`).

| Input/client | Target-visible `User-Agent` | Result |
|---|---|---|
| curl default (`curl/8.22.0`) | `<browser>` | normalized |
| header absent | `<browser>` | normalized |
| explicit `AuditExplicit/1.0` | `AuditExplicit/1.0` | preserved |
| explicit recognizable `curl/8.22.0` | `<browser>` | normalized at a generic proxy hop |
| same curl UA plus ARTEX preserve marker | `curl/8.22.0` | preserved; marker absent at origin |
| Python requests default | `<browser>` | normalized |
| Python urllib default | `<browser>` | normalized |
| Go `net/http` default | `<browser>` | normalized |
| Node built-in fetch | `node` | **not normalized** |
| Git smart-HTTP probe | `git/2.55.0` | **not normalized** |
| headless Chromium | `<browser>` | normalized |

The marked request validates the deployed local proxy boundary, not the
JWT-protected native-tool endpoint itself. It confirms that this boundary strips
`X-Artex-Internal-Preserve-User-Agent` before forwarding.

Both requests in HTTP and HTTPS redirect chains carried `<browser>`. The main
matrix produced 20 origin requests, including browser favicon activity.

### Bodies, redirects, and protocols

- A 1 MiB fixed-length upload arrived with the exact expected length and SHA-256.
- A 384 KiB chunked upload arrived intact. A direct/proxy comparison with a
  second 128 KiB sample showed that ARTEX changed target-visible framing from
  `Transfer-Encoding: chunked` to `Content-Length`.
- A 224 KiB chunked response arrived intact at the client with the expected
  SHA-256.
- HTTP and HTTPS redirects completed, and the final requests remained normalized.
- Verified HTTPS to `https://localhost:<ephemeral>` succeeded through the MITM.
  The local receiver observed TLS 1.3, `TLS_AES_256_GCM_SHA384`, HTTP/1.1 ALPN,
  and an HTTP/1.1 upstream request in this constrained test.
- Verified HTTPS to the same receiver by IP literal failed hostname validation:
  the MITM leaf presented for `127.0.0.1` had no matching IP subject alternative
  name. No insecure retry was made.
- Every origin request in this test used HTTP/1.1.

### Proxy-related headers

No sampled origin request contained `Via`, `Forwarded`, `X-Forwarded-For`,
`X-Forwarded-Host`, or `X-Forwarded-Proto`.

Plain-HTTP curl and Git requests did contain
`Proxy-Connection: Keep-Alive`. A direct curl baseline did not. This is a
proxy-mode libcurl header which the embedded proxy forwards instead of removing;
it is target-visible evidence of an intermediary. It was absent inside the HTTPS
MITM request and from the tested Python/Go/Node clients.

### Capture-off persistence

The read-only traffic-index aggregate remained:

```text
exchange count:       1 -> 1
maximum exchange ts:  unchanged
index mtime:          unchanged
WAL size:             0 -> 0
```

It stayed unchanged in both the 20-request matrix and a separate direct/proxy
comparison run. The one existing row predated this audit and was not inspected.
This is behavioral evidence that the deployed normalization hop did not persist
these exchanges. The authenticated settings endpoint was intentionally not used,
so the control-plane toggle value was not independently read.

## Residual target fingerprints

UA replacement is working on the covered paths, but it is not browser
impersonation:

1. **Browser client hints contradict the replacement UA.** Chromium 152 reached
   the origin with `Sec-CH-UA` identifying Chromium 152 and
   `Sec-CH-UA-Platform: "Linux"`, while the UA claimed Chrome 141 on Windows.
   Its navigation/fetch headers, encodings, language, and favicon behavior also
   remain browser-specific.
2. **Node and Git retain recognizable UAs.** Host Node fetch sent `node` plus
   `Accept-Language: *` and `Sec-Fetch-Mode: cors`; Git sent `git/2.55.0` and
   `Git-Protocol`. Neither UA matches the current normalization list.
3. **Non-browser header profiles remain.** For example, normalized curl still
   sent only `Accept: */*` plus the leaked `Proxy-Connection`; Python requests
   exposed its encoding/connection profile; Go exposed its own minimal header
   set. Header presence, values, casing/order, and connection reuse distinguish
   these clients even when the UA matches.
4. **Transport semantics remain distinctive.** The proxy de-chunks requests,
   presents its own TLS ClientHello, and used HTTP/1.1 in this sample. Packet-level
   JA3/JA4, HTTP/2 settings, TCP behavior, and exact header ordering were not
   measured and can fingerprint the embedded Go proxy.
5. **The static profile ages independently of the browser.** The tested Chromium
   major was 152 while the shared profile claimed 141.
6. **IP-literal HTTPS has a certificate compatibility gap.** A verifying client
   could not accept the generated MITM leaf for the loopback IP.

## Source-informed risks not exercised against the running process

These were left untriggered to avoid credentials, persistent writes, proxy
failure, or disruption:

- Norma v0.4.3 WebFetch retries directly with `norma/0.4` after selected proxy
  errors. That retry bypasses both normalization and a configured proxy.
- Hosts placed in the embedded proxy's TLS pass-through map cannot have encrypted
  headers rewritten.
- The native HTTP custom tool sets the internal preserve marker for any configured
  proxy transport, while only the ARTEX local proxy is known to strip it. An
  explicit-UA tool using an arbitrary external proxy could expose the ARTEX-named
  marker to that proxy or the origin.
- Shipped `api-recon` scripts use explicit
  `Mozilla/5.0 (spa-api-recon...)` UAs, which are not recognized as tool defaults.
  Its runtime re-fetch path also depends on Node environment-proxy support; the
  Docker Node 20 path was not available for this host-only runtime test.

## Limitations

- The authenticated native custom-tool test endpoint, enrichment, and full agent
  runs were not invoked because doing so would require credentials and/or write
  application state. The local hop marker was therefore tested directly.
- No Playwright package or recognizable scanner CLI was locally available;
  installed Chromium was used for the headless-browser path. No package was
  downloaded.
- Only host Node 26 was tested, not the Docker Node 20 runtime.
- No proxy failure or TLS pass-through state was induced in the running ARTEX
  process.
- The HTTPS receiver supported HTTP/1.1 only, and no packet capture or JA3/JA4
  computation was performed.
- The Chromium safety guard changed the hop-by-hop `Connection` header to
  `close`; client hints and other end-to-end headers were forwarded unchanged.
- The global upstream-proxy setting was neither read nor changed.

## Recommended follow-up

1. Strip `Proxy-Connection` and other hop-by-hop proxy headers before forwarding.
2. Decide whether Node/Git and shipped script UAs should normalize, and add
   runtime regression cases for every supported client.
3. Align or suppress Chromium client hints with the selected profile, or document
   that the policy is only UA de-branding rather than browser impersonation.
4. Scope the internal preserve marker strictly to the embedded local proxy and
   prevent direct fallback paths from bypassing target policy/global routing.
5. Add verified IP-SAN MITM coverage and capture-off integration tests for
   redirects, chunking, large bodies, and persistence.
